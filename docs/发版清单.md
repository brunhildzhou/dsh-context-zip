# 发版清单

把一次版本发布要做的事按顺序列出来，每步都写清做什么、怎么验证。这份清单来自 0.1.6 以来各次发布的实际操作，踩过的坑直接写在对应步骤里。**写坑的时机是发现它的那一步**：凡是提交之前就能知道的，一律并进同一个发布提交；只有装到真机之后才暴露的，才留到「六、发布后」。等到 tag 之后再补，代价是一次额外推送，而且 tag 指向的那一版清单里没有它。

前置：三棵树内容一致（开发树、发布树、镜像）。发布树里 `test/run.mjs` 与 `install.mjs` 都是脱敏版，与开发树有固定的脱敏差异：往它们里面加内容只能按 hunk 插入，不能整文件覆盖。**整树 rsync 会静默破坏脱敏**，0.1.8 那次就是这么把真实会话号、本机绝对路径与内部文档引用带进了提交，差点推上去。加完用 `diff` 复核差异规模没有变大，并在推送前跑一次脱敏审计（`cleanroom-mask` 技能，全程只读）。

## 一、改版本号与说明

1. 三棵树的 `package.json` 版本号一起改。
2. 仓库里所有指代**插件版本**的地方同步：根 `README.md`、`README.en.md`、`dsh-context-zip/README.md`、`docs/功能文档.md`、`docs/结构与文件职责.md`。指代宿主版本的地方（形如 `0.1.7-alpha.1`）不动，`RELEASE-NOTES.md` 里旧版本那几节也不动。
3. `RELEASE-NOTES.md` 顶部版本号改成新版本，并在上一版那一节之前插入新一节，写清症状、根因、修法、影响面。
4. 套件条数口径换成本次实测值。条数随运行主体变化。0.1.8 实测两档：开发树当主体并同时给出 `--installed` 与 `--deliverable` 是 1396 条，只给 `--installed` 是 1386 条。第三档「发布树当主体」在发布树上跑不成：发布树不带 `node_modules`，`test/build/lib/segments.js` 解析不到 `@deepseek-ai/*`，直接报 `Cannot find package '@deepseek-ai/dsh-llm'`，要跑得先给发布树种 peer 软链。别照抄上一版的数字，先跑再写。
5. **三棵树的清单文件一次改齐，不留尾巴**。`dsh-context-zip/package.json` 与 `dsh-context-zip/engine/package.json` 都在改动范围内时要一起同步。0.1.9 那次先只同步了前者，后者漏到「二」跑完才发现，结果带 `--deliverable` 的那次套件验的不是终态的树，等于白验一遍。

## 二、重建与验证

1. **先把夹具准备好再开跑**。`--installed` 必须指向 `install.mjs` 装出来的夹具，不能指向 profile 里那份 npm 安装副本：npm 包的 `files` 白名单不含 `test/`，套件要加载 `<目标>/test/build/lib/segments.js`，指错了直接报 `Cannot find module`。夹具 profile 还需要一个能解析 `@deepseek-ai/*` 的根，只往上放一份 `@deepseek-ai/dsh-compaction-basic` 不够：上游守卫会把 `base.js` 抄进 `<夹具>/node_modules/.cz-upstream-guard-*/backend.mjs` 再导入，那里还要 `schemastery` 等包，缺了会报 `Cannot find package '@deepseek-ai/schemastery' imported from ...`，并连带 6 条判据变红。做法是把 `<夹具 home>/profiles/node_modules` 软链到 `DATA/profiles/node_modules`。**先单独确认夹具跑得起来，再进下面的步骤**：0.1.9 那次把夹具问题混在验证里，套件白跑了三轮。
2. 改过 `src/` 或 `client/index.ts` 之后必须跑 `node build.mjs` 重建 `lib/`，否则套件拿旧产物比对，会出现「期望是新的、包还是旧的」假红。
3. `npx tsc --noEmit` 零错误。构建末尾 `tsconfig.types.engine.json` 报的那两条 `engine/engine.ts` 类型错误是既有的，与本插件改动无关。
4. 主口径套件全过：`node test/run.mjs --installed <夹具>/node_modules/dsh-context-zip --deliverable <发布树>`。这一跑要对着**冻结后**的发布树做，带 `--deliverable` 的只此一次；之后再动发布树，这次验证就不算数。
5. 新增的判据必须做反向对照：把修复回退掉，确认这条判据真的会红，再恢复并重跑确认变绿。
6. `npm pack --dry-run` 看包名、文件数与 shasum。0.1.8 起新增两个独立产物 `lib/threshold.js` 与 `lib/types/threshold.d.ts`，文件数从 37 变 39；先确认它们在 `lib/` 里、也在 pack 清单里。顺手把 shasum、sha256 与文件数抄下来，「四」要用它们对 npm 上的值。
7. **两条接线路径都要验**：命令行 `node install.mjs --profile-dir <profile 目录>` 与设置面板那一行的按钮（`src/wire.ts` → `wireCompactionRow`）各接一次，装完对照戳 `redirect/base.json` 的 `patch` 与 `base.js` 里的阈值表达式形态。
8. **认不出的后端要拒绝**：拿一份把阈值表达式改成别的写法的后端，确认接线被拒、重定向目录与 profile 一个字节没动，报错点名「阈值表达式」并提示 `--stock-backend`；再加 `--stock-backend` 跑一次，确认照原样接线、戳记 `none`。
9. **`--check` 要能抓出补丁漂移**：手改 `base.js` 里的阈值形态（或把戳里的 `patch` 改掉）再跑 `--check`，确认按落后处理、退出码 1，那行 `redirect patch ...` 与文件实际形态一致。
10. **这一步踩到的坑当场补进本文件**，与发布树的其他文档一起进「三」的那一个提交，别留到「六」。

## 三、提交与推送

1. 在发布树仓库提交。提交前把本次能知道的东西都收进来（文档、说明、本清单），一个提交装齐；标签之后再改就是第二次推送，而且 tag 指向的那一版里没有它。
2. `git push origin main`。
3. `git tag -a v<版本> -m "<版本>" <提交>`，然后 `git push origin v<版本>`。本机 SSH 走 443；这条链路偶发抽风（`Connection closed ... port 443`），失败就隔几秒重试，不要改 remote。
4. 推送前确认要推的提交本身干净：`git show HEAD:<脱敏文件> | grep -cE '<泄漏串>'` 为 0。发现泄漏而且还没推送时，用 `git reset --soft origin/main` 把整次发布压成一个干净提交重做，不要用追加提交掩盖，留在历史里就等于公开。

## 四、发布

1. 在发布树的 `dsh-context-zip/` 目录里 `npm publish`。
2. 核对 `npm view dsh-context-zip@<版本> dist.shasum` 与本地 `npm pack` 产物的 sha1 一致。
3. GitHub Release 走网页 UI（本机没装 `gh`）：打开 `releases/new`，选 tag，标题写 `v<版本>`，正文粘当次写的 Release 文案，附上 `npm pack` 出来的 tgz，勾 **Set as the latest release**。
4. 发完拉一次附件直链，确认能下且 sha1 与 npm 上的 shasum 相同。

## 五、装到真机

1. **先放行新版本**。宿主机如果启用了新发布包冷却策略（pnpm 的 `minimumReleaseAge`），profile 的 `pnpm-workspace.yaml` 里那份 `minimumReleaseAgeExclude` 白名单要加上这次的新版本号。不加上，安装只会 prune、不会换版本，而且命令照样打印 `Done`，看起来像成功。0.1.6 与 0.1.7 连着踩过两次。
2. 安装用明确版本号，在 profile 目录里跑 `pnpm add -E dsh-context-zip@<版本>`。`-E` 是 `--save-exact`，profile 里手写的依赖都是精确版本，不加会写成 `^<版本>`，风格就变了。`dsh plugin --profile <名字> add <包>@latest` 在 0.1.7 那次连跑两遍都没换版本（`Packages: -2`、`added 0`），原因没有完全定位，先避开 `@latest`。这套子命令本身是把参数透传给 pnpm，`dsh plugin --profile <名字> --help` 打出来的是 pnpm 的帮助。
3. 装完核对三处：profile 的 `package.json` 声明、`node_modules` 里那份的 `package.json` 版本、以及 `lib/index.js` 的 sha 是否与发布树一致。
4. 重启 DSH。重启后看 `/dsh-context-zip/live` 的 `effective.source`、以及 `/dsh-context-zip/wire` 的 `wired` / `stale` / `foreign` / `attention`，与这次改动的预期对照。
5. 重启不会打断接管，**不需要重新接管**（0.1.5 起实测，0.1.7 重启后再次确认）。
6. **装完确认重定向还在**。重定向目录 `node_modules/@deepseek-ai/dsh-compaction-basic` 不在 lockfile 里，pnpm 的 prune 步骤有理由把它当多余目录删掉。0.1.8 那次 `pnpm add` 打印 `Packages: +1 -2`，重定向与补丁都还在，但这一步必须验：看 `base.js` 的字节数、两种阈值形态的计数、`base.json` 里的 `patch`，再跑一次 `node node_modules/dsh-context-zip/install.mjs --profile-dir . --check`，期望 `redirect patch ratio-only` 与 `in sync`、退出码 0。真被剪掉就重新接管一次。

## 六、发布后

1. **装到真机与发布之后才暴露的**坑补进本文件。提交前就能知道的坑按「二」第 10 条当场写，不要留到这里。
2. 更新对外收录（awesome-dsh-plugin 等渠道），再按渠道表逐个推进。
3. 内网或自用机器的升级同步（本机 profile 之外，还有别的实例的话）。
