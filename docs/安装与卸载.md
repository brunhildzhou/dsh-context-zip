# 安装与卸载

本文说明 `build.mjs` 与 `install.mjs` 的分工、安装器每个参数的准确行为、装完为什么要重启，以及回滚怎么做。参数说明照 `install.mjs` 的 `Usage:` 与注释写。

## 构建与安装是两件事

`build.mjs` 负责把源码编译成可运行产物：宿主半边 `lib/index.js`、浏览器半边 `lib/client.js`、引擎 `engine/lib/*.js`，以及 `lib/types/**` 与 `engine/lib/types/**` 里的声明文件。

`install.mjs` **不构建**。它只做纯文件复制：

1. 把本目录（连包内的 `engine/`）与 `redirect/` 两件复制进 profile 的 `node_modules`（复制时排除 `node_modules`、`.git`、`graphify-out`，也不复制 `install.mjs` 自己；`test/build` 故意保留，检查套件要从装好的这一份里读它）；
2. 把 `dsh-context-zip` 加进 profile `package.json` 的 `dsh.profile.bundles`；
3. 把当前解析到的真实后端入口复制成 `redirect/base.js`，并写下版本戳 `redirect/base.json`；后端是宿主 `0.1.7` 那种两项取小的形式时，复制的同时把压缩触发阈值表达式改回只有比例的形式。

所以安装前必须先构建。用打包好的发布副本安装时，构建产物已经在 `lib/` 与 `engine/lib/` 里，不需要再跑 `build.mjs`；用源码树安装时先跑 `npm run check` 或 `node build.mjs`。

三步都是文件复制，删掉那两个目录与 bundle 清单里的一行就完全回退。

## 用 `dsh plugin add` 安装

```
dsh plugin --profile <profile 名> add dsh-context-zip
```

这条命令把插件装成 profile 的普通依赖（由 pnpm 管理），并自动把它登记进 bundles 清单。它**只装插件本体**：压缩那一行仍然是内置后端，装上之后要补一次「接管」——打开设置面板的 ContextZip 一节，点那一行右端的按钮，重启宿主后生效。升级时把版本换掉再跑一次即可：

```
dsh plugin --profile <profile 名> add dsh-context-zip@<版本>
```

装完之后有两条实测事实值得记住：

1. **pnpm 不会动重定向。** 重定向目录 `node_modules/@deepseek-ai/dsh-compaction-basic` 不属于任何依赖，但 `pnpm add` 不把它当多余目录清掉。实测（2026.09.22）：在真机 profile 的完整副本上跑 `add`，重定向的四个文件与其中的版本戳一个字节都没变；随后在真机 profile 上同样验证通过。
2. **所以接管只需要做一次。** 只要这个 profile 接过管，之后用 `dsh plugin add` 升级插件都不会破坏它，不必每次重新接管；重启宿主后那一行会自己回到「已生效」。

另外，pnpm 11 会把新发布的版本号追加进 profile 的 `pnpm-workspace.yaml` 里的 `minimumReleaseAgeExclude`（供应链「最小发布年龄」放行名单），属正常现象。

## `--profile-dir` 怎么给

```
node install.mjs --profile-dir <dir> [--uninstall | --purge | --check] [--home <dir>]
                 [--yes-unnamed-home] [--stock-backend]
```

给的是 **profile 目录本身**，不是 harness home，也不是工作区根。例如 `<harness home>/profiles/web`。

参数解析按 `--flag value` 成对读取，不认识的 flag 被忽略。`--profile-dir` 缺省时取当前目录。

`--profile-dir` 指错路径时安装器在**任何写入之前**就停下：它先确认那里有 `package.json`，报错写明「这不像一个 DSH profile，请传 profile 目录本身」。旧版本会先建好 redirect 包、再读 profile 清单，于是填错路径会留下装了一半的目录，然后抛一个裸 `ENOENT`。

**哪个 harness home 由 `--profile-dir` 决定，不由 `DSH_HOME` 决定。** 这一条只影响 `--purge` 删哪份插件数据。推导线索按顺序用两条：先看 profile 的真实路径往上两级那层目录名是不是 `profiles`（即 `<home>/profiles/<name>`）；推不出来时看调用者写的那个形状，因为 harness 解析 profile 走的是词法路径，`<home>/profiles/<name>` 里的 `<home>` 就是一个能跑到这个 profile 的 home。两条线索都不成立时，`--uninstall` 不给 `--home` 就拒绝执行，一个字节都不动。

`DSH_HOME` 与推导结果不一致时，脚本把两者都打印出来，再按推导结果走。

## 已经装过一次之后重装

重定向装上之后，profile 里 `@deepseek-ai/dsh-compaction-basic` 这个说明符由重定向占着，宿主真身留在包管理器的 store 里，不在 Node 的查找路径上。所以第二次安装不能靠解析去找后端，改为读重定向戳 `base.json` 里记的 `source`。那条路径也失效时（宿主升级后旧版本目录被清掉之类），安装会拒绝，并提示把一份真包放到 profile 的上一级 `node_modules/@deepseek-ai/dsh-compaction-basic`，不会猜一个后端来装。设置面板那个按钮走同一层兜底，否则它只能接线一次、之后再也修不了。

`--check` 用的是同一层兜底：版本读不到就显示 unknown 并且不据此判落后，补丁状态行照常读。

## `--check`

```
node install.mjs --profile-dir <profile 目录> --check
```

`redirect/base.js` 是安装那一刻从内置后端复制的快照。升级 harness 会换掉内置后端，而这份副本不会自己更新，插件会继续按旧后端的逻辑压。

`--check` 把副本里的版本戳与今天解析到的版本比一下，并打印四行：重定向包住的版本与复制时间、harness 今天装的是哪个版本、一行 `redirect patch ...`（从 `base.js` 字节回读的补丁形态）、结论。

| 情况 | 输出 | 退出码 |
|---|---|---|
| 版本相同 | `in sync` | 0 |
| 版本落后 | `STALE: the backend changed since this redirect was installed; re-run without --check to refresh it` | 1 |
| 戳承诺的补丁形态与 `base.js` 里的不符 | 按落后处理，并给出那行 `redirect patch ...` | 1 |
| 这个 profile 里没有重定向 | `no redirect stamp at <路径>: dsh-context-zip is not installed in <profile>` | 2 |

补丁形态这一路看两种情况：戳里记的是 `ratio-only` 或 `not-needed`，而文件里不是那个形态；或者戳里没有 `patch` 键（早先版本装下的重定向），而文件是未补形态。两种都按落后处理，退出码 1。

刷新办法是不带 `--check` 重跑一次安装。

这条检查排在删除动作之前，因为版本戳就住在安装路径最先删掉的那个 redirect 目录里。

## `--stock-backend`

```
node install.mjs --profile-dir <profile 目录> --stock-backend
```

接管时会把复制过来的后端里那处压缩触发阈值表达式定点改回只有比例的形式（原因见 `docs/功能文档.md` §一.9）。改写只认两种后端：宿主 `0.1.7` 那种两项取小的形式，以及 `0.1.5` 到 `0.1.6-alpha.2` 那种本来就只有比例一项的形式。两种都不是（或者两种形式各出现多次这种含糊情况）时默认拒绝接线：什么都不删、什么都不写，报错信息点名「阈值表达式」并提示这个开关。

加上 `--stock-backend` 就照原样接线，不补阈值，戳里的 `patch` 记 `none`。适用场景是后端里既没有 `0.1.7` 那一项、也不是只有比例一项，而你确认要先用着：这时插件不碰那处表达式，压缩触发阈值完全按后端自己的算法走。

设置面板那一行的按钮背后是同一条接线路径（`src/wire.ts` → `wireCompactionRow`），它没有参数，遇到认不出的后端只会拒绝，报错信息指向这个开关。要在这种后端上接线，只能在命令行跑一次带 `--stock-backend` 的安装。

## `--uninstall`

```
node install.mjs --profile-dir <profile 目录> --uninstall
```

只清 profile 那一侧：

- 删掉两个包目录 `node_modules/dsh-context-zip`（引擎在这个包内，不再单独装）与 `node_modules/@deepseek-ai/dsh-compaction-basic`；早先版本留下的 `node_modules/dsh-context-zip-engine` 也会一并清掉；
- 从 profile `package.json` 的 `dsh.profile.bundles` 里滤掉 `dsh-context-zip` 一行。

保留 `<harness home>/context-zip/` 下的笔记、导出，以及 `settings.yaml` 里的 `context-zip:` 命名空间，并把保留了什么打在屏幕上。

## `--purge`

```
node install.mjs --profile-dir <profile 目录> --purge
```

在 `--uninstall` 的基础上，再递归删掉 `<harness home>/context-zip/`。

| 动作 | profile 里的两个目录 | `<harness home>/context-zip/` | `settings.yaml` 的 `context-zip:` 段 |
|---|---|---|---|
| `--uninstall` | 删 | 保留 | 保留 |
| `--purge` | 删 | 删 | 保留 |

保留设置段是刻意的：重装之后接着用，不用重新配一遍。设置段没有删除接口，要清只能手工改 `settings.yaml`，脚本会把这句话打在屏幕上。

`--purge` 删的是**推导出的那个 home** 名下的 `context-zip/`。此时 `--home` 归一化后与推导结果不同就直接拒绝执行，报错点名两边分别是哪个目录。只有 home 彻底推不出来时 `--home` 才是唯一答案，而且那种情况下 `--purge` 还要过下一节的确认。

## `--home` 与 `--yes-unnamed-home`

`--home <dir>` 手工指定 harness home。它只在两条推导线索都推不出来时才是答案；home 推得出来时它不决定删除目标，脚本会打一行说明它在这里不决定任何事。

`--yes-unnamed-home` 是形状认不出时那一次显式确认。触发条件是两条同时成立：

1. 两条 home 推导线索都推不出（路径既不是 `<home>/profiles/<name>`，canonical 路径里也没有一层叫 `profiles`）；
2. 本次是 `--purge`。

此时不带这个开关就拒绝执行，退出码非 0，报错写清三件事：为什么拒绝、它会删什么（`<你给的 --home>/context-zip`，递归删除，里面是笔记与导出）、下一步补上开关重跑。只给开关不给 `--home` 同样拒绝：开关只能确认一个由 `--home` 指名的 home，不能替它命名。拒绝发生在任何删除之前。

形状能推出 home 时，以及 `--uninstall`，这个开关不参与判据。它也不会解锁上一节那个「`--home` 指到别人家」的守卫。

## 软链守卫

写删一律先确认落在 profile 内。软链对读写方是透明的：`cp` 与 `writeFile` 会跟过去，递归 `rm` 会在软链指向的地方删，而 profile 里「某个包名是软链」是常见布局。

现在的做法是先把 `<profile>/node_modules` 的真实路径解析一次并通过守卫，这一次判定覆盖整棵子树；之后所有安装目标都相对这个真实路径拼，并在落地前把已有的那一段逐级展开再确认不会指到 profile 外。`<profile>/package.json` 单独查，因为它自己可能是一条指到外面的软链。卸载分支对三个目录逐个查。拒绝发生在任何写入或删除之前，报错会点名是哪条路径、展开到哪里、以及改法。

合法的软链布局（指向 profile 内的包软链、`node_modules` 本身指到 profile 内的 `vendor/`、profile 目录自身是软链）照常安装。

遇到 `redirect` 位置放着别人真正的 `@deepseek-ai/dsh-compaction-basic` 时，安装与卸载都会拒绝，不会先删掉再报错。

## 装完为什么必须重启宿主

DSH 在启动时组合 profile：读取 bundle 清单、应用各 bundle 的 patch、把插件的 `apply()` 跑起来。`install.mjs` 改的是磁盘上的包与清单，已经跑着的进程不会重新组合，所以 `compaction-basic` 那一行在重启前仍然指向旧实现。

重启之后才会看到：压缩走本插件的五段式摘要、设置左栏多出 `ContextZip` 一节、输入框旁多出压缩方式芯片、四个历史工具上线。

## 回滚到上一份快照

安装器本身**不提供快照或版本回滚**，它只做文件复制，也没有留下任何自动备份。回滚靠重新安装：

1. 解压或取回上一份发布副本（或内部快照 `内部开发快照`）的完整目录树；
2. 在该目录里跑 `npm install` 与 `node build.mjs`，得到那一版的构建产物；
3. 对它跑 `node install.mjs --profile-dir <profile 目录>`；安装器会先删掉三个目标目录再复制，覆盖式安装，所以旧版会被完整替换；
4. 重启宿主。

安装器是幂等的：同一个目录重复装、或装另一份目录，都不会残留上一版的文件。

要回到「完全没有这个插件」的状态，用 `--uninstall`（保留笔记与导出）或 `--purge`（连笔记与导出一起删）。

**会话日志从来不在安装或卸载的范围内**，因为本插件一个日志事件都没写过，所以卸载不可能弄坏任何会话。

## 安装前提

`install.mjs` 要从 profile 的解析路径上找到真实的 `@deepseek-ai/dsh-compaction-basic`，才能复制 `base.js`。这个包由 `$DSH_HOME/profiles/node_modules` 这个 fallback 目录提供，而该目录是 harness 首次启动时才生成的。所以一个从未启动过的全新 profile 装不了：先启动一次，或先把 `$DSH_HOME/profiles/node_modules` 准备好。

找不到时脚本抛 `cannot locate a shipped @deepseek-ai/dsh-compaction-basic from <profile>`。
