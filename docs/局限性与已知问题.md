# 局限性与已知问题

本文集中说明本插件的边界、已知问题，以及内部文档与代码不一致的地方收敛成了什么发布口径。每条都指出依据在哪个文件。

## 一、适用范围与默认状态

### 只支持 DSH 宿主

本插件是 DSH 插件，不能独立运行。它依靠宿主的 bundle patch 机制挂载自己，依靠宿主的 `compaction` 单槽服务接管压缩行，依靠宿主的 `sessionQuery`、`llm`、`settings`、`webServer` 等服务完成取标题、探活、读写设置与暴露路由。脱离 DSH 这些都不存在。

依据：`dsh-context-zip/package.json` 的 `peerDependencies` 与 `dsh.bundle.patch`；`dsh-context-zip/install.mjs` 文件头；`dsh-context-zip/README.md`。

影响：没有 DSH 的部署用不了。

### 工作笔记默认关

`enabled` 默认 `false`，新会话交给内置后端压（`DEFAULT_ENABLED = false`，`src/index.ts`）。笔记功能本身没有独立开关：它的门就是压缩模式，`notes_write` 在按内置后端压缩的会话上直接回「this session compacts with the shipped backend, so notes are off for it」。

依据：`dsh-context-zip/src/index.ts` 的 `DEFAULT_ENABLED`；`dsh-context-zip/src/tools.ts` 的 `notesWriteTool.execute` 门；`docs/功能文档.md` §二。

影响：不显式打开开关，工作笔记与五段式摘要都不会生效。插件注册的七个工具都在，其中只有一个写工具 `notes_write` 在这个状态下会被拒（`src/tools.ts` 的 `notesWriteTool.execute` 门），`notes_read` / `notes_search` 仍可读——代码注释写明这个读路径要「在笔记模式关掉之后仍能读到已写的笔记」。

### 检索节流的效果从未确立

`throttle` 默认 `false`（`DEFAULT_THROTTLE = false`，`src/index.ts`）。开启后它会做四件事：给每次检索加回执、已完整持有的事件不再返回、连续两次零新增后暂停 `history_search` 与 `history_find`、收窄期间给读取设上限。

它的**效果**没有确立。同四格跑三次，对基线的 token 比落在 **0.10× 到 8.46×** 之间；已发表的工作报告激进节流会掉准确率。功能文档的实测状态总表把回执与增量过滤、收窄、读一次换一次搜索、收窄期间读取上限四行全部标为「未证实」。所以这四件事默认关着，代码保留。

依据：`dsh-context-zip/src/index.ts` 里 `throttle` 字段的 schema `description`（0.10× 到 8.46× 与掉准确率那句）；`docs/功能文档.md` §六「实测状态总表」四行与它下面那句结论（「节流那一整层（索引表 §3）的效果全部未证实」）；`dsh-context-zip/README.md` 的 `throttle` 行。

**注意台账与打点不受这个开关管辖**：关着时账本与 `tracePath` 照常运行，所以未节流的基线仍然可测。

影响：把这个开关当成省 token 的手段没有依据。要判断它在你自己的任务上有没有用，只能自己跑对照。

## 二、面板与呈现

### 会话名最长 60 秒才更新一次

面板的会话名走插件内的标题备忘录（`src/session-titles.ts`），过期时间是 `TITLE_TTL_MS = 60_000`，即 60 秒。首次读设置时立刻用备忘录里现有的名字回答，冷或过期的折叠在响应之后于后台跑，5 秒一跳的 `/live` 把晚到的名字补进面板。

依据：`dsh-context-zip/src/session-titles.ts` 的 `TITLE_TTL_MS`；`dsh-context-zip/src/routes.ts` 与 `dsh-context-zip/README.md` 的「设置」一节。

影响：刚改过会话名时，面板上最多 60 秒还是旧名。

### 标题备忘录没有容量上限

备忘录用普通对象与集合按会话号累积名字（`createTitleMemo` 里的 `resolved`、`supported`、`absent`、`wanted`，都是无界容器），代码里没有逐出条数或容量上限，只有 60 秒的过期时间。过期只决定「什么时候重取」，不决定「丢掉哪些键」。

依据：`dsh-context-zip/src/session-titles.ts` 的 `createTitleMemo`。

影响：长期运行的进程里，覆盖表提到的会话号越多，这份备忘录持有的键就越多。它只存短字符串，量级由面板实际碰过的会话数决定。

### 按会话覆盖表在面板上只读

`agents` 与 `retrievalAgents` 两张表在面板里都没有输入框、行内开关、删除钮、新增钮、保存钮。每会话覆盖的唯一写入口是输入框旁的压缩方式芯片（按会话号写一行），或手工改 `settings.yaml`。面板里的行只显示会话名与一个复制会话号的按钮。

依据：`docs/功能文档.md` §十二「覆盖表变成只读」与「面板结构」；`dsh-context-zip/client/index.ts`；`dsh-context-zip/README.md` 的「设置」一节。

影响：要写 agent 预设名那一档的覆盖，只能改 `settings.yaml`。

### 压缩模式是现读的，不是创建时冻结

面板翻总开关会立刻改变**已经开着的**会话的下一次压缩。会话的模式是「你问的那一刻设置是什么」的函数，不随会话创建定格。输入框旁的芯片在切会话时走只读路由 `GET /dsh-context-zip/mode?sessionId=…`，那条路由调的是引擎每次压缩前调的同一个 `resolveMode()`。

那条路由只认本进程持有的会话，拿不到就答 404，芯片显示成暗红色、开关不可切换（点它不会换后端，而是重试读取；`client/index.ts` → `onLabelClick`）。正常的 GUI 会话都在同一个进程里，只有页面留着一个服务重启前的旧会话号时才会看到这个状态。

依据：`dsh-context-zip/src/index.ts` 的 `resolveMode` / `resolveModeFrom` 与 `applyRetrievalVisibility`；`dsh-context-zip/src/routes.ts`；`dsh-context-zip/README.md` 的「压缩模式的按会话切换」与「输入框那一排的压缩方式开关」。

### 全局开关不拦 `/zip-compact`

那个开关管的是自动压缩那一步用哪套摘要。`/zip-compact` 命令始终可用，裸发只报计划、加 `--yes` 才动手，关着敲它仍会压缩，只是那一次的摘要由内置后端写。

依据：`docs/功能文档.md` §十与§十一；`dsh-context-zip/src/manual.ts`；`dsh-context-zip/README.md` 的同一节。

## 三、安装与升级

### 安装器不构建

`install.mjs` 只做文件复制。它不会跑 `build.mjs`，所以拿一份没有构建产物的源码树去装，装出来的 `lib/` 是空的。

依据：`dsh-context-zip/install.mjs` 文件头与安装分支；`docs/安装与卸载.md`。

### 升级 harness 后重定向会落后

`redirect/base.js` 是安装那一刻从内置后端复制的快照，不会自己更新。升级 harness 会换掉内置后端，而这份副本仍旧。`--check` 把副本里的版本戳与今天解析到的版本比一下，落后就报 STALE 并以退出码 1 结束。刷新办法是不带 `--check` 重跑一次安装。

依据：`dsh-context-zip/install.mjs` 的 `--check` 分支；`docs/安装与卸载.md`。

### 全新 profile 装不了

`install.mjs` 要能从 profile 的解析路径上找到真实的 `@deepseek-ai/dsh-compaction-basic` 才能复制 `base.js`。该包由 `$DSH_HOME/profiles/node_modules` 提供，而那个目录是 DSH 首次启动时才生成的。

依据：`dsh-context-zip/install.mjs` 的 `basePackageDir`；`dsh-context-zip/README.md` 的「前提」段；`docs/安装与卸载.md`。

### 没有快照与版本回滚

安装器不留任何自动备份，也不提供版本回滚子命令。回滚只能重新构建并安装上一份发布副本，或直接跑 `--uninstall` / `--purge` 回到未安装状态。

依据：`dsh-context-zip/install.mjs` 全文（无备份与回滚分支）；`dsh-context-zip/README.md` 的「脚本做三件事，都是纯文件复制，删掉两个目录就完全回退」；`docs/安装与卸载.md`。

## 四、文档与代码不一致的收敛结果

内部功能文档在几处描述与代码不一致。下面逐条给出发布口径：哪几条已经修掉、哪几条仍在、分别有什么影响。

### 已修掉：套件条数

内部功能文档曾把套件记作 943 条，随后又更正为 919 条。发布副本实测为 **1360 条**（同时给出 `--installed` 与 `--deliverable` 两个参数）。收录的 `docs/功能文档.md` 已把这两处数字改成 1273。

依据：`evidence/套件说明.md` 的实测命令与输出；`docs/功能文档.md` §七与§十二。

影响：只影响文档里那个数字，不影响任何行为。

### 已修掉：面板的「只读行」判据说明

内部功能文档说套件里「既没有只读行、封顶步长、气泡定位的行为判据，也没有源码文本判据」，同时又说补了一组 13 条源码文本判据。前半句不准确：套件里有覆盖表转换与保存方向的判据（`toRows` 与 `rowsAfterSave` 一组），它管的是「哪一次保存可以覆盖表」这条更危险的行为。

仍然没有写进套件的是：只读列表的渲染形态、显示更多的封顶与步长、问号气泡的定位与翻转。这三样靠一次性渲染 fixture 与真机验收覆盖。

依据：`dsh-context-zip/test/run.mjs` 的 `toRows` / `rowsAfterSave` 断言组（标签前缀 `save rows:`）与同文件里那段说明「列表形态、封顶步长、气泡定位这些行为判据不在这里」的注释；`docs/功能文档.md` §十二「套件」小节。

影响：面板那三处改动以后不会再被套件自动拦住，只能靠人工验收。

### 已修掉：压缩模式是否冻结

内部文档与旧面板文案都写过「快照在会话创建时读取，会话存续期间不随这里改动而变」。这与实现相反：模式是现读的。面板文案已改成如实说明，两套语言都改了。

依据：`dsh-context-zip/README.md` 的「本轮开发中发现并修掉的问题」里那两条（面板文案与只改中文那一套）；`dsh-context-zip/src/index.ts`。

影响：无遗留。这条现在在两套语言里都说得对，且有一条结构性检查盯住两套键集合一致。

### 已修掉：`/zip-export` 的参数与作用域

内部文档记录过两个缺陷：命令没声明 `input` 描述符导致带参数的命令从 GUI 到不了 handler；导出走的是 live-only 的 `sessionOf`，对不在本进程里的会话直接抛错。两处均已修，导出改走支持从存储重建的 `sessionFor`。

依据：`dsh-context-zip/README.md` 的「本轮开发中发现并修掉的问题」；`dsh-context-zip/src/export.ts`。

### 仍在：格式改写护栏的实测数字分散在两处口径

功能文档 §六 的实测状态总表里，「格式改写护栏」一行写的是「误退 0/522、真编造召回 12/12、注入七形状 7/7」，并把甲口径的历史数指向 §九；而 §九 的实测表写的是丁口径（判据 1）的结果：W1 与 W2 两种改写形状误退都是 0/522，真编造召回 12/12，注入七形状 7/7；甲口径（集合差）那两个数是 1.1% 与 1.9%，注入七形状 5/7。

两处说的是同一批 522 格语料上的两个不同口径。代码走的是丁口径。

依据：`docs/功能文档.md` §六与§九；`dsh-context-zip/engine/engine.ts` 的 `introducedPaths` / `sameFileSpelling` / `rewriteGuardBlocks` 与 `rewriteProseLayout` 的实际调用（先 `rewriteGuardBlocks`，`addedClaims` 在产品路径上没有调用点，只有测试引用）。

影响：读这两处数字时要看清口径；不要把它与「摘要一致性检查（B10）」的数字混在一起，后者是另一件事。

### 仍在：折行探针的代价

丁口径下折行探针 P1 从 15/522 涨到 259/522（2.9% 到 49.6%），P9 从 81 涨到 123，P6 从 3 涨到 11。功能文档 §九 自己把它列为「两处还没调」之一：折行那 49.6% 的缓解，正确落点在提示词。

依据：`docs/功能文档.md` §九「代价（必须一起看）」与「两处还没调」。

影响：护栏在这一点上的收益与代价要一起读，不能只引误退率。

### 仍在：「第一次拨动会把 `enabled: false` 固化进 `settings.yaml`」

设置段本来不存在时，第一次改设置会把默认值物化。类型和取值都对，但面板的「新会话默认」会从「默认值，尚未设置过」变成「来自设置」，并钉死一个 `false`，将来改 `DEFAULT_ENABLED` 影响不到这些 home。

这一条内部记录为明确不修：修它要动设置读写两侧对「缺省键」的约定，得先做一轮设置层的往返实测，风险大于收益。

依据：`dsh-context-zip/README.md` 的「本轮开发中发现并修掉的问题」里标注为「记录不修」的那一条；`dsh-context-zip/src/index.ts` 的 `applySettingsPatch` 与 `writeSettings`。

影响：面板会显示「来自设置」而实际值等于默认值。

### 已修掉：保存一次覆盖表会重置别的设置

`applySettingsPatch` 曾经只带四个键，而写路由最后用 `scope.replace` 提交整段，于是 `throttle`、`fallbackEnabled`、`fallbackAfterFailures`、`tracePath` 会被抹掉并由 schema 补回默认值。现在补丁里写了就用补丁的，没写就用当前生效的。

依据：`dsh-context-zip/src/index.ts` 的 `applySettingsPatch`；`dsh-context-zip/README.md` 同一份问题清单的最后一条。

## 五、能力边界

- **只读自己**：四个历史工具只读调用者自己的会话，不跨会话、不跨智能体。
- **不往会话日志写任何东西**：插件写进会话日志的事件数是零。压缩产生的三个事件全部由内置后端写，类型和格式都不是本插件定的。插件自己的状态只有工作笔记与导出，都在 `<harness home>/context-zip/` 下。
- **摘要是唯一权威**：工作笔记只作为「意图材料」并入摘要，事实以历史为准。
- **检索工具不吃 `enabled` 开关**：`registerTools` 在插件加载时无条件调用，所以 `enabled: false` 只关掉压缩，四个历史工具连同节流照样上线。
- **`history_read` 从不出现在遮罩列表里**：这是有意的，代码里有注释说明。
- **笔记有 6000 字符上限**：草稿接近上限时会丢掉最旧的条目，新写的条目本身也可能被截断，两种损失在工具结果里分别措辞。

依据：`dsh-context-zip/src/tools.ts`、`dsh-context-zip/src/notes.ts`、`dsh-context-zip/engine/prompt.ts`、`dsh-context-zip/README.md` 的「这个插件不往会话日志里写任何东西」一节、`docs/功能文档.md` §二「关键事实」。
