# 套件说明

本插件自带的运行时检查套件是 `dsh-context-zip/test/run.mjs`。它逐条断言，末尾打印一行结果：

```
context-zip: 1359 checks passed
```

失败时打印 `context-zip: <N> of <M> checks FAILED` 并列出每条失败，退出码 1。通过时退出码 0。

## 它检查什么，不检查什么

套件检查的是**构建产物**，不是 TypeScript 源码。

`test/entry.ts` 的唯一用途是把检查要用的内部符号重新导出。`build.mjs` 把它一起编译成 `test/build/lib/segments.js`，`test/run.mjs` import 的是这个产物。所以打包出错（漏掉一个导出、把引擎 inline 进产物、声明文件没生成）也会被测出来，而不是只测源码逻辑。

`test/entry.ts` 从不被插件自身引用。

## 怎么跑

三步。工作目录是 `dsh-context-zip/`。

1. 构建。

   ```bash
   node build.mjs
   ```

   这一步产出 `lib/index.js`、`lib/client.js`、`engine/lib/*.js`、三趟声明文件，以及被测的 `test/build/lib/segments.js`。

2. 同步到被测树并安装。

   ```bash
   node install.mjs --profile-dir <测试 profile>
   ```

   套件读的是**装好的那一份**，所以要先装一次。安装器会排除 `node_modules`、`.git`、`graphify-out`，但**保留 `test/build`**，正是为了让 `--installed` 指过去时能读到它。

3. 跑检查。

   ```bash
   node test/run.mjs --installed <安装目录> --deliverable <交付目录>
   ```

   两个路径的常见取值：

   ```bash
   node test/run.mjs \
     --installed <测试 profile>/node_modules/dsh-context-zip \
     --deliverable .
   ```

## 两个参数各做什么

| 参数 | 作用 | 不给会怎样 |
|---|---|---|
| `--installed <插件目录>` | 告诉套件被测主体在哪。套件从这里读 `test/build/lib/segments.js`，并**顺带**从同一个 `node_modules` 里找到宿主自带的压缩后端 | 套件回落到本仓库的 `test/build/lib/segments.js`；`@deepseek-ai/*` 解析不到，加载阶段直接失败 |
| `--deliverable <包目录>` | 把这个目录的 `package.json` 也交给 `checkDeclaredTypes`：逐个核对 `exports[*].types` 指向的文件是否存在 | 只查本仓库那一侧，交付树缺声明文件不会被发现 |

`--installed` 同时决定了两件事：被测主体，以及上游守卫要对比的那份真实后端。两者都从同一棵 profile 树来。

## 为什么不给 `--installed` 会假报失败

构建把 `@deepseek-ai/*` 与引擎**保持为外部依赖**，不 inline。这样进程里只有一份引擎模块，插件注册的模块级读取器就是被挂载的那个引擎读到的那个。代价是检查必须对着**能解析这些包名的**树跑，而本仓库自身不含 harness。不给 `--installed` 时有两种表现：

1. **加载阶段就失败**。`loadSubject()` 捕获 `ERR_MODULE_NOT_FOUND`，抛出一条说清该怎么做的话：构建把 `@deepseek-ai/*` 留成外部依赖，所以检查只能跑在 profile 能回答这些说明符的地方，并打印那两行安装与运行命令。
2. **一份能加载、但上游守卫假报失败的结果**。这是更隐蔽的一种：手动压缩那一组检查要真的 import 宿主自带的 `selectCompactableRange`，把它的选段结果与插件移植过来的那一段逐例对比（11 个手写形状加 240 个固定种子随机表面）。拿不到那份后端源码时，守卫报的是「探针加载不到依赖」，报不出「两边选出的区间不同」：

   ```
   manual guard: the shipped backend could not be probed, so nothing was compared
   ```

   实测不带 `--installed` 跑一次，末尾是这几条 `manual guard` 失败、一条 `range-too-small` 失败，外加一条 `build exit code: the plugin tree is reachable for the build probe` 失败（没有 `--installed` 就拿不到被测树），退出码 1。（本节写下的那次复跑实测共 `8 of 982 checks FAILED`。）

所以看到红的先确认参数给全了，再判断是不是真缺陷。

## 当前条数

**1359**。在发布副本上实测：

```bash
# 前提：这个副本里已装好开发依赖（typescript 与类型声明），否则类型与构建探针拿不到工具链
node build.mjs
node install.mjs --profile-dir <临时 profile>
node test/run.mjs --installed <临时 profile>/node_modules/dsh-context-zip --deliverable .
# context-zip: 1359 checks passed
```

不接 `--deliverable` 时是 1348 条，差额是交付树那几条 `exports[*].types` 声明指针检查与来源 kind 检查（本次实测 10 条）。

条数会随功能增加而变。引用条数时写明是哪个构建上跑出来的。

**构建时序**：`lib/` 与 `engine/lib/` 是构建产物。改了 `client/index.ts` 或 `test/run.mjs` 之后，必须重跑 `node build.mjs` 再跑套件或打包，否则会出现「期望是新的、包还是旧的」这种假红。2026.09.23 改提示词动作时就遇到过一次：`test/run.mjs` 已更新成期望新的接管命令，而 `lib/client.js` 还是改动前的构建，套件报出一条 `attention: the bubble carries the repair prompt` 失败，重跑构建后消失。

## 判据覆盖哪几大类

按 `test/run.mjs` 里各段的实际内容归类。条数指的是这一段里的断言数，会随改动漂移，所以只给类别与它们在断言里的落点。

另有一条**格式层判据**：冻结的 V4 会话 fixture 先经宿主自己的 `Session.create` 重建，再比对插件分段管线派生的段号、被替换事件号与摘要事件号。

### 1. 压缩主流程

分叉会话的段号是否只数自己的压缩、段号与摘要事件号的对应、按事件号找所属段、段与回合的推导（`deriveSegments`、`deriveTurnStart`、`segmentForSeq`）、分叉划界的三种来源优先级（`inheritedEventCount` 必须赢过落盘标记与进程内构造事实）、分叉会话的日志读取优先级与回退（活跃会话自己的 `snapshotEvents()` 优先，查询服务退为备用）、上下文窗口的取值与回退（先读最后一条 `request/context`，读不到才查模型目录）。

摘要指令与形态：`classifySummary` 的三支判决、`buildSummarizationInstruction` 的拼装、段级溯源 `attributeSummarySections`、编造检查 `findUnsupportedClaims` / `auditUnsupportedClaims` 的 scope 行为。

### 2. 检索工具与节流

三种消息载荷（用户消息、助手消息、工具结果）的转写投影、转写超预算的截断标记、单条超预算事件必须仍能读到开头、被寻址的事件必须出现在窗口里（含「长条目在前、目标在后」这种两次验收都踩过的形状）、转录预算的精确适配（单条目与多条目、分隔符只付一次）、搜索下界的取值（一位之差，取承载这次调用的助手消息之前）、游标的自包含与翻页（跨增长、跨插入搜索、跨重新铸造都不重页）、认不出来的游标必须拒绝而不是当第一页返回、逐词寻址与缺席点名、`history_find` 的截断措辞与词数上限。

节流侧：`throttle` 总开关（含默认关）、回执的几种措辞、增量过滤与覆盖区间的判定、收窄状态机与读取上限、台账容量、打点字段。

### 3. 兜底与重排

机械兜底的形状与触发条件（失败计数按尝试算、达到阈值后落地、`fallbackAfterFailures` 的夹取）、失败分类 `isRangeTooSmallFailure` 沿 `cause` 链的判定、改写路由的解析（开关关、未选 provider/model、选中后的路由）、最低思考档位的选择次序表、改写调用的请求形状（输入只有那份摘要、`system` 逐字、无对话独有句子）、护栏的集合差与判据 1（`introducedPaths`、`sameFileSpelling`、`rewriteGuardBlocks`、只加标题与折行的形状必须不被拦）。

### 4. 设置与路由

设置命名空间与 schema 的默认值与边界、`applySettingsPatch` 的合并语义（补丁没提到的键用当前生效值、`agents` 表按替换而不是合并、全是垃圾行时报错而不是静默清空）、模式查表的两级优先级（会话号优先于 agent 预设名，三档回落）、来源判定（`settings` 还是 `default`，靠 `describe().user` 里真正出现的字段区分）、按会话分流的四条路径（默认委托、插件路径、行配置覆盖上限、读取器缺失时的回退）、两个会话在同一进程里得到相反答案。

插件自己的 HTTP 路由：`/mode` 的三种回答（本进程持有、不持有、id 格式错）、`/live` 的载荷（与整读同一个 `effective`、不带设置值、带上标题备忘录）、`/settings` 与 `/live` 的漂移守卫、无 webServer 的 profile 不抛错、轮询的健康记账与节奏常量。

### 5. 面板文本与结构

两套语言对象的键集合必须一致；那条曾经只改中文、英文留着假话的文案，两种语言都要通过与「现读」一致的检查；会话号判据只有一处原文（`SESSION_KEY` 的正则逐字比对）；面板文案里不许再出现「冻结」类表述。

面板源码文本：旧写路径 `updateRow`、`commitRows`、`setRows(`、`keyPlaceholder`、`agents-add` 必须消失；`复制会话 id`、`isSessionKey`、`显示更多`、`收起信息`、`dsh-context-zip__srow-name` 与 `dsh-context-zip__srow-name--id`、两条 `panel-copy` 常量必须在。

### 6. 面板重写

覆盖表行的转换 `toRows` 与保存后 `rowsAfterSave`：哪一次保存可以覆盖表。开关的保存必须原样保留未保存的行（浏览器里量过 `rowCount: 1` 变 0 而屏幕写着「已保存」），表自己的保存必须刷新行；空回答与缺回答都清空表；挂载读用的是同一处转换，两边不会漂开。

整页保存：草稿、脏净比较与那颗唯一的保存按钮（四个脸的源码形状、可点性判定、`strings.saving` 的渲染点）。

**没有写进套件的**：只读列表的渲染形态、`显示更多` 的封顶与步长、问号气泡的定位与翻转。这三样靠一次性渲染 fixture 与真机验收覆盖。

### 7. 会话标题

标题备忘录 `createTitleMemo` 与 `TITLE_TTL_MS`：过期后重取覆盖整张表、按批次合并而不是替换（一个键失败不能清掉别的名字）、宿主不返回可用标题的键记为缺席且不再重复问、重入按刷新而不是全局锁、失败吞进 `warn` 而不让轮询路由产生未处理的 rejection。

名字晚到的那条链：首次 `/settings` 只答备忘录里已有的名字、折叠在响应之后于后台跑、`/live` 那一跳必须把 `titles` 并进 state，否则面板开着时改的会话名要关掉重开才看得到。

### 8. 整页保存

同第 6 类里的「整页保存」一组。用户 2026.09.20 定下的四件事在这里钉住：控件一改就写盘改成整块草稿加一处保存；保存按钮进标题行最右；成功变勾、失败红底，各停 1.5 秒；草稿与服务端相同时按钮置灰不可点。脏净比较与可点性判定是纯函数，直接跑；按钮位置走真渲染树。

## 还有两组不在上面的分类里

- **构建与交付面**：`build.mjs` 在「删了声明却没能重新生成」时的退出码三情形（没有 typescript 且声明在、没有 typescript 且声明缺、有 typescript 但某一趟没产出）；`checkDeclaredTypes` 对 `exports[*].types` 的逐条核对，以及「一个都查不到」这种情况本身必须失败。
- **安装器的 home 推导**：`--profile-dir` 决定 home、`DSH_HOME` 从不决定；`--home` 与推导结果不一致时 `--purge` 拒绝；形状认不出时 `--yes-unnamed-home` 是唯一出路；用两个 home 各放一个哨兵文件钉住「purge 之后目标 home 的哨兵必须没了、另一个 home 的必须还在」；软链逃逸的 10 个逃逸场景与 8 个合法场景。

## 开发依赖与条数的关系

发布包里**不带 `node_modules`**。要跑套件，先在插件目录装一次开发依赖（`npm install`，四项都在 `package.json` 的 `devDependencies` 里：`typescript`、`esbuild`、`@types/node`、`@types/react`）。

装了依赖时套件**全过**；没装时**有 1 条会失败**：`build exit code: typescript is reachable for the third case`（构建探针要能从这个插件树里找到 `typescript`）。2026.09.23 实测：交付树（不含 `node_modules`）自己当运行主体时是「**1 of 1344** checks FAILED」（同一棵树接上 `--deliverable .` 是「1 of 1354」，失败仍是这一条），失败的正是这一条；其余全过。安装使用不需要这些依赖，只有跑套件需要。
