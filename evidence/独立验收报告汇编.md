## C6 — `history_search` pagination — **FAIL**

The criterion has two clauses: the cursor must yield *subsequent* hits, and must not repeat the first
page. The first clause holds while the bound is unchanged. The second fails as soon as the session
grows between the two calls, which is the normal case: the upper bound is defined as one below the
assistant message that requests the call, and requesting page 2 always appends a new assistant
message, so page 2's bound is necessarily larger than page 1's.

Control — bound unchanged between the pages (`<tmp>/zcr1/logs/c-tokens.out`):

```
P token-p1 => 3 matching event(s), strongest first: #122 … #109 … #95 …
P token-p1-cursor="3" filters=[{"kind":"seq","to":129},{"kind":"text","text":"short"}] hits=15
P token-p2-sameBound => 3 matching event(s), strongest first: #82 … #105 … #89 …
P token-seqs => p1=[122,109,95] p2same=[82,105,89] p2moved=[122,109,95]
```

Same session, after it grew by three matching events (bound 129 -> 169):

```
P token-scored@129=[[122,2],[109,2],[95,2],[82,2],[105,1],[89,1],[78,1],[72,1]]
P token-scored@169=[[163,2],[149,2],[136,2],[122,2],[109,2],[95,2],[82,2],[105,1]]
P token-p2-movedBound => 3 matching event(s), strongest first: #122 … #109 … #95 …
P token-p2-movedBound-filters=[{"kind":"seq","to":169},{"kind":"text","text":"short"}] hits=18
```

Minimal reproduction — exactly **one** new matching event arrives between the pages
(`<tmp>/zcr1/logs/c-c6min.out`, `ZC_PART=c6min`):

```
P c6min-p1 => 3 matching event(s), strongest first: #122 … #109 … #95 …
P c6min-cursor="3"
P c6min-p2-movedBound => 3 matching event(s), strongest first: #95 … #82 … #105 …
P c6min-seqs => p1=[122,109,95] p2=[95,82,105] overlap=[95]
P c6min-new-hit-source seq136 type=user/message
```

Expected: `带上游标再查能拿到后续命中，且与首页不重复`. Actual: page 2 repeats `#95` from page 1, and in
the wider case repeats page 1 verbatim.

Mechanism (code + the observed scored lists): this profile composes `session-query-sqlite` with
`openAt: never` (`--dump-config`), so `searchEvents()` throws
`SESSION_QUERY_SEARCH_DISABLED` and `history_search` always uses the in-memory fallback
`filterSearchPage()`. Its cursor is an **offset into a score-sorted list that is recomputed on every
call** (`scoreText` = occurrence count, ties broken by descending seq). Because the bound moves
forward, newly eligible events enter that list; on a tie, the newer seq wins, so the new entries sort
ahead of the older hits and shift the window back over the previous page. The probe's replica of
`scoreText` reproduces the served pages exactly (`token-scored@129` vs `@169` above), including the
`p2moved=[122,109,95]` page. The defect is not a fixture peculiarity: in a real session page 2's
window always contains page 1's own `tool/result`, and that result always echoes the query word in
every snippet it returns, so at least one new matching hit with a competitive score is guaranteed
between the two pages. **C6 FAIL.**

## R1 — repair 1: `readSessionEvents` prefers the live snapshot — PASS

Claim under test: the review tools work in a forked (seeded) session and list only the child's own
segments from ordinal 0, not the parent's.

Evidence is the C2 block above, taken through the tool surface (not through the internal helper):
before the child's own first compaction it answers with the empty-list sentence while 5 inherited
summaries sit in its log; after its own compactions it lists exactly its own 5, numbered 0..4, and
in a later process it still does.

The premise in the code comment is real, not defensive hand-waving: on the same grown child,
`sessionQuery.readSession()` throws `seeded session constructor seed must equal its inherited prefix`
both in-process and after a fresh-process resume (`R1-readSession`, `R1-reopened-readSession`), while
`query.observeSession()` succeeds (`ok events=128 inherited=64`). Preferring
`session.snapshotEvents()` is therefore what makes C2 pass at all; had the two been reversed, every
review tool in a forked session would surface that constructor error. **R1 PASS.**

Residual observation (not a failure; flagged for the author): the fallback branch in
`readSessionEvents` returns `[]` when `sessionQuery` is absent and otherwise calls
`query.readSession()`, which is exactly the call that throws for a seeded session that has grown past
its prefix or compacted. Any future caller that reaches that branch with a forked session will get
either an empty directory or the constructor error, so the fallback is only safe for unseeded
sessions.

## R2 — repair 2: `history_search` cannot match its own invocation — PASS

Fixture `r2s1` is a real log in which the model invented the token `QZ7X4MKP9TWR2BDV` in the very
turn that searched for it: the token occurs at seq 157 (`assistant/message`, the carrier), 158
(`tool/call`, the invocation) and 159 (`tool/result`) and nowhere before 157 — checked mechanically
over the raw log. The probe replayed seqs 3..160 live, so the plugin's `assistant/message` listener
ran for seq 157 exactly as in a real turn. `<tmp>/zcr1/logs/c-search.out`:

```
P R2-carrier assistant/message=157 boundary=156 tool/call=158
P R2-invented => No event in this session matches "QZ7X4MKP9TWR2BDV".
P R2-filter-seen => {"filters":[{"kind":"seq","to":156},{"kind":"text","text":"QZ7X4MKP9TWR2BDV"}],"n":0}
P R2-control => 2 matching event(s), strongest first: #89 tool/result [segment 7]: … ZQMARKER77 …
P R2-filter-control => {"filters":[{"kind":"seq","to":156},{"kind":"text","text":"ZQMARKER77"}],"n":24}
P R2-raw-occurrences<=160 => 157:assistant/message,158:tool/call,159:tool/result
```

The bound is visible at the service boundary (`{kind:'seq', to:156}`, boundary = carrier seq - 1), the
invented word returns zero hits although its own `tool/call` event is in the log when the handler
runs, and the same bound still returns 24 real hits for a control word, so the fix does not simply
blind the search. **R2 PASS.**

Residual note (not a failure of the claim as worded): the bound comes from an in-process map filled
by live `session/event` notifications, so it is guaranteed only while the process has seen the
carrier message. That holds for every search issued from an agent turn, because the carrier
`assistant/message` is appended before the `tool/call` executes; a tool call invoked with no
preceding assistant message (as in this probe) is unbounded, but that is not reachable from the
model-facing loop.

### T3c — new robustness observation: a malformed cursor is served as page 1

Not a regression against round 3 (same codec), but a change from rounds 1-2 and worth a
decision. My `also` fixture hands the tool a legacy bare cursor `"1"` for a one-hit search:

```
PROBE normal history_search({"query":"normal opening line"}) => 1 matching event(s), strongest first: #3 user/message: normal opening line That is the last page.
PROBE normal history_search({"query":"normal opening line","cursor":"1"}) => 1 matching event(s), strongest first: #3 user/message: normal opening line That is the last page.
```

The continuation returns page 1 again instead of `No further match`. Cause: `"1"` does not match
`^(\d+)~(\d*)$`, so it is treated as an opaque service cursor; the side table has no entry for
it (that search minted no cursor at all, since it had no next page), so the boundary falls back
to the live bound and `filterSearchPage` sees `decodeSearchCursor(...) === null` and uses
offset 0. The same shape is visible in `fix2`'s contrast line, where a hand-written `"10"` is
served as offset 0 under the live bound (`33,30,27,…` — neither page 1 nor page 2):

```
PROBE old-style-page2(10)=33,30,27,26,25,24,23,22,21,20
```

Reachability: a cursor the tool minted in this profile is always `<offset>~<bound>`, so this
needs a hand-written or mangled cursor (e.g. a model transcribing `10~27` as `10`), or a cursor
from the indexed service whose side-table entry was evicted. Effect is a silent wrong page
rather than an error. If you want it closed, the fallback could treat a numeric-only cursor as
an offset (the round-1 behaviour) or refuse a cursor it cannot resolve; I am not counting it
against FIX2.

### Behaviour worth flagging (not a claimed defect, judgement call for the owner)

## FAIL 详述

### D7 — 笔记长度上限没有返回提示（FAIL）

判定依据原文：「反复写入直到超限，返回里带有被截断的提示，而不是静默丢弃」。

**最小复现**

1. `<tmp>/zctest2/home/settings.yaml` 写 `context-zip: {enabled: true}`。
2. 一个 headless 会话里让模型调用一次 `notes_write`，`text` 参数约 7000 字符，首行 `HEADER-PART-TAILMARK-alpha`、末行 `TAILMARK-omega-END`（本报告的构造：`<tmp>/zctest2/work/d7-task.txt`，11302 字节）。
3. 读该次 `tool/result` 的文本，并读落盘的笔记文件。

**原始输出**

```
seq=15 CALL notes_write arglen=11125
seq=16 RESULT len=2 -> 'ok'
```

落盘（该会话压缩后归档到 `seg-000.md`）：

```
$ wc -c <tmp>/zctest2/home/context-zip/notes/session-<示例>/seg-000.md
5957
$ head -1
[earlier notes dropped: per-session limit reached]
$ tail -1
TAILMARK-omega-END
$ grep -c HEADER-PART-TAILMARK-alpha seg-000.md
0
```

**期望 vs 实际**

- 期望：返回里出现「被截断 / 有内容被丢弃」的提示。
- 实际：返回只有 `ok`（`NOTES_WRITE_ACK`）。截断只留在文件首行 marker 与插件日志里，模型侧看不到。
- 成因（读码佐证）：`src/tools.ts` 的 `notesWriteTool` 在 `outcome.trimmed === true` 时只调用 `options.warn?.(...)`；`render` 分派只有 `ok === true → NOTES_WRITE_ACK`，输出 schema 的 `reason` 字段只在 `ok:false` 时渲染。
- 影响：模型会以为自己刚写下的意图已完整保存，实际最旧条目已被丢掉，且它无法从返回里知道要重写。

**语义歧义（重要，如实记录）**：条文「返回里带有被截断的提示」的「返回」有两种读法，我都实测了。

- 读法 A：指 `notes_write` 自身的返回 → **FAIL**（返回是裸 `ok`，见上）。
- 读法 B：指事后 `notes_read` 的返回 → **PASS**。在 web profile（无激进压缩补丁）里补做：模型写 8405 字符的笔记后立刻 `notes_read`，返回
  `'Live notes draft for this session:\n\n[earlier notes dropped: per-session limit reached]\n- [00:50] f0001 f0002 …'`（6036 字符），marker 可见。

本报告按读法 A 判 FAIL，因为条文主语是「反复写入直到超限」这一动作，落在该动作上的「返回」自然是写入调用自己的返回；但若验收方取读法 B，D7 应为 PASS，且唯一的真实缺陷降级为「写入返回不提示、需再读一次才知道」。

## UNCONFIRMED 详述

### D6 — 笔记是否进入摘要材料（UNCONFIRMED）

做法：会话里先写一条含关键词 `BANANA-77` 的笔记，再触发多次压缩，检查 `compaction/summary` 正文是否含该关键词。

观察：多次压缩的摘要确实含 `BANANA-77`。

试过的排除办法：`compaction/summary` 事件只带 `summary/rawOutput/usage/…`，不含摘要调用的入参；会话日志里没有可观察「笔记材料被喂进摘要调用」的字段。
结论：按「无法复现观察到的东西就报 UNCONFIRMED」的规则记录。代码路径（`setSharedNotesReader` → 引擎 `summarize()`）看起来接通，但没有独立可观察证据。**没有假报 PASS。**

## 额外发现（不在编号项内，但值得修）

1. **面板文案与会话行为矛盾**：设置面板底部写「…快照在会话创建时读取，会话存续期间不随这里改动而变」，而 E3 实测同一会话运行中改设置后压缩写法立刻切换，README 也明说「模式是实时读的，不在会话创建时冻结」。该句文案与实现相反，会误导用户。
